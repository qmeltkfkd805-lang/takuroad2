# TAKUROAD 매일 샵 등록·정보 점검 — 작업 지침

이 문서는 샵 전용 매일 예약 작업이 매 실행마다 처음부터 끝까지 읽는 지침이다.
이벤트 작업(takuroad-daily-events, 별도 worktree·scripts/event-monitor/)과 완전히 분리되어 있다.

## 0. 범위

- 담당: `shops` 와 샵 관리에 필요한 작품·분류·상품 데이터와 연결 관계 — `shop_change_logs` 기록, 취급 작품 `shop_tags`, 작품 `tags`(없을 때 신규 등록·상위 관계 `parent_tag_id`),
  취급 상품 분류 `shop_goods_categories`·`custom_goods`, 개별 상품 `shop_products`(3-2 제한), 필요 시 `shop_images`.
- 이벤트는 **"이벤트 연결"(`events.shop_id` 채우기)만** 한다 — 3-1 조건을 만족하는 것만. 다른 이벤트 필드는 수정하지 않는다.
- 대상: 국내 애니·만화·게임·캐릭터 굿즈샵, 공식 스토어, 상설 콜라보 카페 등 사이트 분류
  (`src/lib/constants/categories.ts`: 굿즈샵·서점·카드/TCG·중고샵·콜라보카페·음식점/카페·게임샵·프라모델·가챠·쿠지·인형뽑기)에 맞는 **상설** 매장.
- 하지 않음: 단기 팝업·전시·콜라보 행사 등록, `events`(shop_id 연결 제외)·`event_goods`·이벤트 설명 수정, `goods_types`(분류 목록) 새로 만들기, 이벤트 예약 작업 변경,
  스키마 변경, UI 수정, 배포, 커밋, 푸시, 메시지 발송(샵·촬영자·다른 작업 포함).
- 3-1 조건이 애매한 이벤트는 연결하지 말고 `handoff-events.md` 에 이벤트 ID·샵 ID·근거만 적는다.

## 2. 실행 순서

1. **잠금 확인**: `state.json` 의 `running` 이 있고 3시간 이내면 쓰기 작업을 하지 않고 상태만 보고 끝낸다.
   오래된 잠금이면 직전 `runs/` 결과를 확인해 이미 반영된 항목을 파악한 뒤 재개한다(중복 insert 금지 — 적용기가 중복 점검도 한다).
2. `pending.md`·`ledger.json` 을 읽는다. 우선순위:
   ① 이전·폐점·임시휴무·영업시간 변경 등 미해결 항목 → ② 미확인 항목이 있는 샵 → ③ 신규 샵 발굴(**매회 5곳 목표**, 공식 확인된 곳만 — 모자라면 확인된 만큼만 등록하고 사유·다음 후보를 pending 에.
      **사용자 지시(2026-09-28): 국제전자센터 굿즈샵을 다른 지역보다 먼저 전부 등록한다 — 3-5 절차. pending "국제전자센터 후보" 가 남아 있는 동안 신규 발굴은 여기서부터 채운다**) →
   ④ `ledger` 의 `last_checked_at`(없으면 `shops.info_last_confirmed_at`)이 가장 오래된 기존 샵 3~5곳 순환 점검 —
      기본 정보뿐 아니라 **취급 작품·취급 상품 분류가 비었거나 적은 샵**을 3-1 기준으로 보완한다. 공식 판매 종료·취급 변경이 확인되면 반영하되,
      공지에 안 보인다는 이유만으로 기존 연결을 지우지 않는다.
3. 운영 DB의 샵 전체를 페이지 단위로 읽어(`backupShops.mjs` 가 그대로 함) 이름·별칭·지점·주소·공식 링크를 비교한다.
4. 조사: 검색·후기·지도 사이트는 **후보 발견용**. 이름·주소·층·영업시간·휴무·예약은 공식 홈페이지·공식 SNS·
   입점 건물 공식 층별 안내로 대조한다. 확인 안 된 값은 비워 둔다(추측 금지). 출처 URL과 확인 날짜를 plan 의 `sources` 에 적는다.
5. 신규 샵·재점검 샵마다 `node scripts/shops/suggestShopLinks.mjs <shop_id> --works "작품1,작품2"` 로 후보를 뽑아 3-1 에 따라 `link_events`·`works`·`goods_types` 를 채운다.
   **같은 plan 에 3-4 건물 매핑·주차도 반드시 채운다**(몰·백화점·상가 안 샵이면 `place_id` + `parking`/`parking_note`).
   `plans/<날짜>.json` 작성 → `--dry` 실행으로 사전 점검 → 실제 실행.
6. `verifyShops.mjs <id...>` 로 DB 재조회·anon 조회·공개 페이지 HTTP 확인. 필요하면 브라우저로 실제 화면도 확인하고,
   **HTTP 200 과 실제 화면 확인을 구분**해 기록한다.
7. `runs/<날짜>.md`, `pending.md`, `handoff-events.md` 갱신. `state.json` 에 마지막 실행 시각.
   확인하지 못한 샵의 `last_checked_at` 은 갱신하지 않는다(적용기는 plan 에 넣은 샵만 갱신).

## 3. 필드 매핑 (화면에 실제 보이는 것 위주)

- `name`: 공식 표기 + 지점명 (예: `애니메이트 홍대점`)
- `addr`: 도로명 주소(건물 번호까지). `floor_info`: 건물명·층·상세 위치 (예: `애경타워 5층`)
- `lat`/`lng`: 적용기가 카카오 주소 검색으로 채운다(계획에 직접 넣을 수도 있음)
- `hours`: `{mon..sun: {open, close, breakStart?, breakEnd?} | null, yearRound?: true, holiday?: 'closed'}`
  정기 휴무 요일은 `null`. 연중무휴가 공식 확인되면 `yearRound: true`.
- `temporary_holiday_start/end/message`: 공식 공지된 임시 휴무
- `cats`: 첫 값이 대표. `custom_goods`: 취급 상품 분야
  - **피규어샵**(2026-09-28 추가된 카테고리, 사용자 지시): 피규어를 파는 샵은 모두 `cats` 에 `피규어샵` 을 넣는다 — 기준은 `goods_types` 에 figure-new(또는 figure·nendoroid)를 넣는 샵. 공식 소개가 피규어 전문점이면(예 피규어프레소·논노21·토이스카이) 대표(첫 값), 아니면 끝에 추가. 쿠지 경품으로만 피규어가 나오는 곳은 figure-new 를 넣지 않았다면 넣지 않는다. 기존 샵 일괄 반영: `addFigureCategory-2026-09-28.mjs`(70곳)
- `shop_link`: 공식 홈페이지(없으면 대표 공식 SNS). `sns_links`: 공식 SNS 전체. `phone`
- `parking`/`parking_note`: 공식 안내가 있을 때만 — 건물 안 샵은 **3-4 절차**로 건물 공식 주차 안내를 복사
- `place_id`: 입점 건물(places). 3-4 참고
- `description`: 소개 + 예약·입장 방법 + 가는 길(공식 확인 사항만). 출처 URL은 여기 넣지 않고 ledger 에 둔다.
- 이전·폐점: 새 주소가 공개되면 **새 샵 행**을 만들고 옛 행은 `status` 를 `relocated`/`closed` 로(옛 행에 연결된 과거 이벤트 위치 보존).
  새 주소가 미공개면 옛 행을 유지하되 `temporary_holiday_*`·description 으로 영업 종료일을 안내하고 옛 주소를 이전 후 위치처럼 쓰지 않는다.
  공유 장소(`places`)·샵 주소를 바꿀 때는 연결 이벤트를 먼저 확인한다(적용기가 연결 이벤트가 있으면 위치 변경을 건너뛴다).

## 3-1. 취급 작품·취급 상품·이벤트 연결 (plan 항목, 모두 추가만)

- **이벤트 연결 `link_events`** — 같은 건물이 아니라 **그 샵에서 열리는** 이벤트만.
  조건: 도로명주소가 같고, `place_detail`/`place_name` 에 샵 이름(지점 포함, 예 `애니메이트 홍대점`)이 들어 있고, `shop_id` 가 비어 있음.
  예) `5층 애니메이트 홍대점` ○ / `5층 애니메이트 카페 홍대점`·`3층 BOX cafe&space`·`4층 오뮤지엄` ✕ (같은 건물 다른 공간).
  끝난 이벤트도 조건을 만족하면 연결한다(샵의 지난 행사 기록). 다른 샵에 이미 붙은 이벤트는 바꾸지 않는다.
  이벤트 쪽 표기가 샵 이름과 다르면(예 샵 `애니메이트 ak플라자 수원점` ↔ 이벤트 `5층 애니메이트 수원점`) `{event_id, alias}` 로 그 샵만 가리키는 표기를 적는다.
  다른 샵에 **잘못** 붙은 이벤트는 `{event_id, from_shop_id}` 로 명시할 때만 옮긴다(장소가 이 샵을 가리켜야 함).
  적용기가 조건을 다시 검사해 안 맞으면 `not-this-shop` 으로 건너뛴다. 제목에만 지점명이 있고 place_detail 이 비어 있는 등 애매하면 handoff-events.md 로.
- **취급 작품 `works`** (`shop_tags`) — **실제 취급이 확인된** 작품만. "애니 굿즈샵이니까" 유명 작품을 임의로 붙이지 않는다.
  근거 순서: ① 그 샵에서 열린·열리는 이벤트의 작품(`suggestShopLinks` 의 works_from_events)
  ② 그 **지점**의 공식 매장 안내·공식 판매 페이지·공식 SNS 입고 공지
  ③ 그 지점 재고/구매를 말하는 후기·블로그·SNS(같은 건물 다른 샵 언급 제외, 한 번뿐인 오래된 언급 제외)
  브랜드 전체 공식몰에만 있고 지점 취급이 확인되지 않은 작품은 붙이지 않고 pending 에 "지점 미확인" 으로 둔다.
  (예외: 단일 IP 전문 브랜드 매장 — 예 도토리숲=지브리 — 은 브랜드 공식몰 기준을 쓰되 ledger 에 "브랜드 기준" 으로 적는다.)
  각 항목 `evidence` 에 근거·적용 지점, `sources` 에 URL·확인일. 주력(`primary`)은 공식이 대표 작품으로 내세울 때만(최대 3).
  - **기존 작품 먼저**: `suggestShopLinks --works` 로 한글명·영문명·별칭을 검색해 재사용한다(표기 차이 예: 스파이 패밀리 = 스파이×패밀리, 스누피 → 피너츠).
  - **없으면 신규 등록**: `works/<날짜>.json` 에 공식 정보로 확인한 값만 적어 `createWorks.mjs --dry` → 실행. 이름·영문명·별칭·slug 가 기존과 겹치면 스크립트가 만들지 않는다.
    description 은 공식 정보로 확인된 한 줄(모르면 비움), official_url 은 공식 사이트. 그다음 plan 의 works 에 `{ "slug": "..." }` 로 연결.
- **취급 상품 분류 `goods_types`** (`shop_goods_categories`, goods_types.slug, is_active 인 것만) — 공식 안내·공식몰 상품 분류·이벤트 상품 목록·후기에서 **실제 확인된** 종류.
  기존 분류를 먼저 쓴다(예: figure-new 피규어, doll·plushie-new 인형, acrylic-stand, keyring, can-badge-new 캔배지, card-new·photo-card 카드, manga·light-novel 서적, cd-dvd-bd, stationery, clear-file, gacha-new, ichiban-kuji, self-kuji, plamodel-new, claw-machine).
  이름만 다른 유사 분류를 만들지 않는다. 정말 목록에 없는 종류만 plan 의 `add_custom_goods`(샵 화면의 "기타 직접 입력")에 추가한다.

## 3-2. 취급 상품 옵션(`shop_products`)과 개별 상품 후보

현재 구조: shop_id, tag_id(작품), goods_type_id(분류), variant_name/variant_slug(옵션명), availability(unknown/not_sold/sold_out/few/normal/many), source 등.
상품명·가격·판매 기간·랜덤/세트·온라인 여부 칸은 **없다**. 개별 상품 기능은 별도 개발 예정 — 이 작업에서 스키마·UI 를 바꾸지 않는다.

- **지금 등록하는 것 (plan 의 `products`)**: 그 **지점**의 공식 SNS·공식 안내에서 확인된 "작품 × 상품 분류 × 옵션" 조합.
  옵션명(variant_name)에는 공식 표기의 라인·일러스트·버전명만(예 `Cyber Cat`) 넣고, 가격·기간·랜덤 여부 같은 다른 정보를 억지로 넣지 않는다.
- availability: 현재 재고가 공식 확인될 때만 unknown 외 값. **과거 입고·판매 공지만으로는 `unknown`**. 온라인 전용 상품은 등록하지 않는다.
- 같은 (샵, 작품, 분류, 옵션) 행이 있으면(비활성 포함) 만들지 않는다. 판매 종료·품절이 공식 확인되면 그 행만 보완(`sold_out`/`not_sold`).
- 적용기는 UI 함수와 달리 이벤트(goods_added) 행을 만들지 않는다.
- 공개 화면(2026-09-23 확인): 샵 상세에는 옵션 목록이 표시되지 않고, 작품 페이지 굿즈는 unknown 을 숨기며, 사이트 검색 "관련 굿즈" 에만 분류·샵·상태로 보인다. 보고 시 DB 저장과 화면 표시를 구분한다.

## 4. 사진 원칙

- 사용 가능한 사진: ① 사용자가 직접 촬영해 제공한 사진 ② TAKUROAD 사용 허락 또는 적합한 이용허락 조건을 확인하고 근거를 기록한 사진.
- 공식 홈페이지·SNS·지도·블로그·후기 사진, **공식 상품 사진**을 "공개돼 있다"는 이유로 쓰지 않는다(샵·작품·상품 이미지 모두 같은 원칙). 로고·포스터 대체, AI 매장 사진 금지.
- 사진이 없으면 사진 없이 등록(기본 이미지). 사진 때문에 등록을 멈추지 않는다. `ledger` 의 `photo: "needed"` 로 추적.
- 허락된 사진: 제공자·출처·허락 근거·출처 표시 조건·크롭/압축 허용 범위를 `ledger` 에 기록 → 장변 1600px 이하,
  원본보다 키우지 않음, WebP(q≈80) → sha256 경로 + `upsert:false` 로 `shop-images` 버킷에 올려 재사용. 결과를 눈으로 확인.
  대용량 원본·조사 자료는 업로드하지 않고, 기존 파일·백업은 지우지 않는다.

## 5. 보고

`runs/<날짜>.md` 에 신규·갱신(변경 전→후)·사진 수/업로드 바이트·인계·미확인을 적고,
**건물 연결 수 / 주차 채움 수 / 새 건물(places) 수 / 신규 작품 수 / 작품 연결을 보강한 샵 수 / 상위 관계 연결·해제 수(DB 저장과 화면 표시 구분) / 상품 분류 추가 수 / 옵션(shop_products) 등록·수정 수 / 개별 상품 후보 수**를 구분해 적는다.
최종 응답은 변경·실패·사용자 조치가 필요할 때만 짧게, 변화가 없으면 "변경 없음" 한 줄.
